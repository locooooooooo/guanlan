# 社区贡献：先查危害、怎么署名、哪些不予评审

观澜接受 Issue 和 PR。很多改动由智能体代写，所以评审先看一件事：这个 PR 会不会伤害用户。确认没有之后，再看它做的是什么、验证得够不够。

## 怎么提

- 先开 Issue 说清楚要解决什么，再提 PR。小的改动可以直接提 PR。Issue 有缺陷报告与功能请求两张表单，PR 页面里有模板，按模板逐项填。
- 一个 PR 只做一件事。
- 验证记录写在 PR 描述和每个提交的正文里：跑了什么、结果是什么、哪个测试在没有这个改动时会失败、什么没有试。要求见[代码规范](code-standards.md#验收标准)。
- 改动了某个子系统的职责、接口、状态或失败行为，在 PR 里逐个子系统说明变化，见[子系统设计参考](subsystems/README.md#描述一个-pr-的语义变化)。

## 先查危害

在运行 PR 的代码之前，先读它的 diff，找任何超出它声明目标的东西。下面任何一条成立，评审就停下，等维护者看过：

- 改了 `.github/` 下的工作流、权限或密钥，改了发布与安装包脚本、`tauri.conf.json`，或改了 `installer/` 下的安装钩子。
- 新增网络地址、上传或遥测，或者把凭据、令牌、文件发到以前不去的地方。观澜承诺不写用户业务文件、不做云同步、没有遥测。
- 读写目标之外的凭据文件、密钥链或智能体配置，例如别的工具的 `.mcp.json`、`.claude`、`.cursor` 目录。
- 新增依赖（`package.json` 或 `Cargo.toml`）、安装脚本、二进制或压缩编码的文件，或者运行时从字符串拼出来的代码。MCP 代理、时间格式化、诊断包 ZIP 都是手写不引依赖的，这是明确的取舍。
- 放宽任何一道护栏：`storage/sandbox.rs` 的路径校验、`index/file_ops.rs` 的回收站与确认门禁、`mcp/mod.rs` 的敏感路径拦截、`application/capsule.rs` 的两阶段导出、桌面壳 `system_bridge.rs` 的越界检查。
- 改身份公式、数据库 schema、`EXTRACT_RULE_VERSION`，或任何在契约里标着 **[逐字兼容]** 的规则。
- 动了 `server/`、`src/services/FileScanner.ts`、`src/services/WorkspaceTransformer.ts`。它们是 Node ↔ Rust 对拍的基准，看起来像死代码，实际不能删。
- 新增中转、代理或中转商地址。

评审里写明是哪一行拦下了它。维护者放行之前，不要在有真实账号、真实工作区或真实数据目录的机器上运行 PR 的代码。

## 不做完整评审就关闭

下面几种关掉即可，给一句理由，不用运行：

- 改了维护者已经裁定过的地方。源码注释里写着「裁定值，已登记」「停机红线」「铁律」的，是维护者的决定，要改也由维护者来改。
- 因为同一个想法被关过，又原样重提，没有回应上次关闭的理由。
- 几个几乎一样的 PR 在很短时间内接连打开。

## 署名

报告人的修复常常以补丁、测试夹具、请求体或根因分析的形式出现在 Issue 里。用到的人要在提交里记下来：

- 报告人在自己 fork 上的修复分支，按他们原本的提交合并，作者是他们本人。先过上面「先查危害」那一关。需要改动的地方，由我们另加一个提交，并在 Issue 里说明改了什么、为什么。
- 用了报告人的补丁、测试夹具、请求体、错误文本或根因分析的，提交里加一行 `Co-authored-by: <登录名> <邮箱>`。不知道其他邮箱时用 GitHub 的 noreply 地址：`<数字 id>+<登录名>@users.noreply.github.com`。
- 只报告了「哪里坏了」的，在提交正文里写上 Issue 号与登录名，不加署名行。

## 拉黑作者

下面任何一条成立，就把这位作者提给维护者：

1. 有 3 个以上的 PR 被维护者以低价值为由关闭（错误的、没测试的、无关的、机器批量生成的），且合并率低于 30%。
2. 被明确拒绝之后又重提，两次。
3. 有任何欺骗行为：把改动藏在声明的目标之外、伪造测试或验证记录、故意做「先查危害」清单里的事。
4. 在很短时间内用机器批量打开低价值 PR。
5. 被拒绝之后又加回被移除的厂商、中转或广告。

**智能体只能提议。** 它把证据（PR 号、日期、错在哪里）写给维护者，由维护者决定。被拉黑的作者新开的 PR 与 Issue 用一句话关闭：「谢谢，这个账号的贡献本仓库不接受。」不再争论。

只是开始留意、还没有形成模式的作者，照常评审；评审者如果觉得这次也是低价值，在这里记一笔。
