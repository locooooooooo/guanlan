一个子系统可以跨多个 crate 或目录。它的参考描述这些部分共同提供的行为，不需要列出每个函数。

## 维护一份参考

一个改动若改变了某份参考里写明的职责、接口、状态迁移、运行路径、兼容规则或失败行为，**在同一个 PR 里更新那份参考**。保持这些契约不变的内部重构不需要改文字。

每个事实只写在一份参考里，其他页面（包括仓库根的 `AGENTS.md`）链接过去。链接源码文件和具名符号，不要复制容易变的实现细节。签名表达不了的字段含义和约束要写出来。

新写一份参考时，包含：职责与边界、事实来源、主要运行路径、状态迁移、重要约束、已有的验证命令；相关的失败行为与兼容行为也要写。**当前行为与提议分开写**，提议属于它的 Issue 或 PR。

## 描述一个 PR 的语义变化

对每个受影响的子系统，说明可观察的变化：触发条件、改动前后的行为。涉及接口、状态、兼容性或失败行为时一并写出。链接对应的参考、实现和验证证据。重构保持了既有行为时，明确说「行为不变」。

例如，一个改了对账缺失判定的 PR，应当说明在哪种采集结果下触发、改动前后分别如何判定缺失、哪个测试覆盖这条路径。

这段由作者提供，评审者对照 diff 与周边代码核实。它不是自动证明出来的兼容性结论。

## 评审一个改动

1. 找出受影响的子系统和实际的运行路径，包括它是走唯一写线程、只读连接池，还是直接落盘。
2. 对照改动前后的实现，核实声称的行为差异。顺着调用方和状态迁移多走几步，不要只看改动的几行。
3. 检查变化了的契约是否写回了对应的参考，源码链接是否仍然有效。
4. 检查引用的测试或运行证据确实覆盖了声称的行为。没跑的检查要写明没跑。

只改文档不能证明实现正确。行为变化仍然需要现有的测试和运行证据。
